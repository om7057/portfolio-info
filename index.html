The recurring pattern across these contributions: code assumes a value, response, or success case is always present, so when it isn't, the failure comes out as a swallowed error, missing data, or a crash instead of a controlled outcome.

Jenkins RemotingPRIssue
  • FifoBuffer.writable() computed Math.max(0, limit - readable()), but readable() returns -1 as a closed-and-empty sentinel rather than an actual count, subtracting it produced limit + 1 instead of 0 exactly when the buffer was closed with nothing left to read.
  • That wasn't just a cosmetic accounting bug: releaseRing() nulls the write pointer under the same readable() < 0 condition, so a write() racing right as the buffer closed could see a positive writable(), skip its closeRequested retry check, and call write() on an already-null pointer.
closeRequested and closeRequestCause read across threads without a happens-before edge
Jenkins RemotingPR
  • Channel.close() and terminate() assign closeRequested/closeRequestCause before entering the synchronized block, but other threads read them without the monitor via isClosingOrClosed() and getCloseRequestCause(), as plain fields, a reader had no guarantee of ever observing the write.
  • Made both fields volatile, matching inClosed/outClosed which were already volatile for the exact same read pattern in the same methods.
Unbounded RPC wait in preOnline() could stall an agent's whole online handshake
Jenkins OpenTelemetry PluginPRIssue
  • preOnline() waited on the agent's OpenTelemetry configuration RPC with an unbounded Future.get(), while the sibling afterConfiguration() already bounded the same kind of call to 10 seconds, since preOnline() runs synchronously inside SlaveComputer.setChannel(), an unbounded wait gave a NAT idle timeout or network blip a much bigger window to close the channel before the handshake finished, mostly hitting agents on higher-RTT links.
  • Bounded the wait to a configurable timeout (default 10s, matching afterConfiguration()), logging a warning and letting the agent online anyway instead of blocking indefinitely when it elapses.
Changelog lock released by a command that never acquired it
LiquibasePRIssue
  • AbstractUpdateCommandStep conflated "a lock exists" with "this method acquired the lock": commands like updateCount rely on the pipeline's LockServiceCommandStep to lock, but run() still tried to release it in its finally block, producing a spurious second release attempt.
  • Added a flag tracking whether run() itself acquired the lock, so only the actual owner releases it; a regression test fails on the previous implementation and passes with the fix.
Non-user RPC requests bypassed the close-in-progress guard and blocked on the monitor close() held
Jenkins RemotingPR
  • Channel.close() sets closeRequested up front and then holds the Channel monitor for the rest of teardown, while outClosed stays null until later, during that window, checkIfCanBeExecutedOnChannel() is the guard meant to refuse new requests, but it was only overridden on UserRequest and RemoteInvocationHandler.UserRPCRequest (identical copy-pasted bodies); the base Request.checkIfCanBeExecutedOnChannel() only checks getSenderCloseCause() (outClosed).
  • So a base RPCRequest, a ProxyInputStream.Chunk, or any other non-user Request sent in that window passed the check and then blocked on the monitor close()/terminate() was already holding, instead of failing fast, moved the guard onto the base Request class so every request type is refused consistently once close is requested.
